# Технический аудит и план: «Наши / Клиентские» + автопроверка ссылок

Документ подготовлен по факту чтения кодовой базы (не по памяти). Ссылки на реальные
файлы/таблицы/поля. Ничего ещё не меняется — это аудит и план.

---

## 1. Как сейчас устроена система

**Стек:** Python 3.12 / FastAPI, SQLAlchemy 2.x, Alembic, Postgres (Railway, EU West).
Фронтенд — ванильный JS (ES-модули, hash-роутер `frontend/js/app.js`), без сборки, отдаётся
тем же backend'ом. Один процесс `uvicorn`, 1 реплика. В `app/main.py` уже есть фоновая
asyncio-задача (`neon_heartbeat`) в `lifespan` — это готовый паттерн для фонового воркера.

**Основной поток работы сегодня (только «наши» проекты):**
1. Импорт **анкор-плана** (Excel/CSV) → `anchor_plans` + строки `anchor_plan_items`.
2. Импорт **доноров** → `donors` (+ `donor_accounts` — аккаунты для входа на донора).
3. **Автоподбор** (`services/matcher.py::auto_match_plan`) проставляет строкам
   `selected_donor_id` по гео/языку/типу ссылки, исключая уже занятых доноров.
4. Менеджер **назначает** строки сотрудникам (`anchor_plan_items.assigned_to`).
5. Сотрудник в «Моих задачах» (`/my-tasks`) берёт задачу (`take_task` → создаётся
   `placements`), размещает ссылку и жмёт **«Разместил»** (`mark_placed`): сохраняется
   `result_url` (**это и есть ready-link**), статус `placed`, запись уходит в **стоп-лист**
   (`stop_list_service.register_placement`).
6. **Дашборд** и **журнал действий** (`audit_logs`) агрегируют/логируют.

**Роли (`app/auth.py`):** `super_admin`, `admin`, `user` (сотрудник).
`require_admin` = admin|super_admin; `require_super_admin` = только super_admin.
Разграничение данных сотрудника: `/my-tasks` фильтрует по `assigned_to == user.id`;
`mark_placed/mark_problem` проверяют `placement.employee_id == user.id`.

**Ключевое правило дедупликации (важно для нового функционала):** уникальность —
**на анкор**, ключ `(target_url, anchor_text, donor_url)`. То есть один и тот же донор
нельзя переиспользовать для того же анкора, но можно для другого анкора (даже с тем же
`target_url`). Это заложено в `stop_list_entries` (UniqueConstraint) и в матчере
(`_blocked_donor_urls_for_target`, `blocked_by_anchor`).

## 4. Изменения в базе данных (обзорно; финальные DDL — по фазам)

Всё **обратно совместимо**: новые колонки `NOT NULL DEFAULT 'internal'` / nullable FK.
Существующие данные автоматически становятся «Наши».

**Расширяем существующие таблицы:**
- `anchor_plans`: `+ kind VARCHAR(16) NOT NULL DEFAULT 'internal'`, `+ client_project_id FK NULL`.
- `anchor_plan_items`: `+ kind` (денормализация для быстрых фильтров, наследуется от плана).
- `placements`: `+ kind`, `+ client_id FK NULL`, `+ client_project_id FK NULL`.
- `stop_list_entries`: `+ kind`, `+ client_project_id FK NULL` (только теги, дедуп не трогаем).
- `users`: `+ client_id FK NULL` (заполнен только у роли `client`), роль расширяет enum-значения.
- `audit_logs`: уже гибкий (`target_type`/`details`) — новые типы событий без схемных правок.

**Новые таблицы:**
- `clients` (id, name, contact_info, status, comment, manager_id→users, created_at, updated_at).
- `client_projects` (id, client_id→clients, name, promoted_domain, geo, language,
  donor_requirements TEXT, planned_count INT, period_start, period_end, status,
  manager_id→users, created_at, updated_at).
- `client_project_members` (client_project_id, user_id) — назначенные сотрудники (M:N).
- `allocation_settings` (id, scope ENUM[global|team|employee], scope_id NULL,
  internal_pct INT, client_pct INT, period_start NULL, period_end NULL, updated_by, updated_at).
- `employee_daily_plans` (id, user_id, date, planned_total, planned_internal, planned_client,
  done_internal, done_client) — план/факт (можно считать «на лету», таблица — для истории/коррекций).
- `link_checks` (id, placement_id UNIQUE→placements, status, level, last_checked_at,
  next_check_at, attempts, expected_url, expected_anchor, expected_link_type,
  final_url, found_anchor, http_status, is_dofollow, error_reason, locked_at, priority).
  — «текущее состояние + очередь» в одной таблице (claim по `next_check_at`/`locked_at`).
- `link_check_results` (id, placement_id, link_check_id, checked_at, status, level,
  http_status, found_url, found_anchor, expected_url, expected_anchor, final_url,
  is_dofollow, redirect_chain JSON, error_reason, raw JSON, duration_ms).
  — **история** (append-only), не только последний результат.
- `notifications` (id, user_id, type, severity, entity_type, entity_id, title, body,
  is_read, created_at) + `notification_rules`/конфиг видимости статусов клиенту.

**Индексы:** `(kind, status)` на items/placements; `link_checks(status, next_check_at)`
для выборки очереди; `link_check_results(placement_id, checked_at)`.

## 7. Роли и клиентский кабинет

**Расширяем enum ролей:** `super_admin` (владелец) → `admin` → `manager` → `teamlead` →
`employee` (текущий `user`, оставляем строку `"user"` ради совместимости) → `client`.

| Роль | Доступ |
|---|---|
| super_admin | всё, включая управление пользователями/сбросы |
| admin | всё операционное: клиенты, проекты, доноры, планы, распределение, мониторинг |
| manager | свои клиенты/проекты, назначение работы, мониторинг, отчёты клиентам |
| teamlead | своя команда: распределение, корректировка планов, мониторинг команды |
| employee | только свои задачи (`/my-tasks`), размещение, добавление ready-link |
| **client** | **только свои** проекты/размещения/отчёты; НЕ видит: доноров, стоп-лист, чужих клиентов, внутренние комментарии, внутренние проекты, техпроцессы |

**Реализация изоляции (двойная защита):**
1. **Зависимость** `require_client` + `current_client_scope(user)` → возвращает `user.client_id`.
2. **Скоуп на уровне запроса:** каждый `/client/*` эндпоинт добавляет
   `.filter(client_id == user.client_id)` — не «скрытие на фронте», а физический фильтр в SQL.
3. Клиентские сущности отдаются через **отдельные `ClientXxxOut` схемы** без внутренних полей
   (без `login_*`, внутренних комментариев, донор-метрик сверх домена).
4. **Тесты изоляции** (§13): прямой API-запрос клиента к чужому `project_id`/`placement_id`
   → 403/404; к внутренним эндпоинтам (`/donors`, `/stop-list`) → 403.

Существующий бэкенд-first подход к правам сохраняем (все проверки на сервере).

## 8. Разделение «Наши / Клиентские»

**Источник истины — `anchor_plans.kind`** (+ `client_project_id` для клиентских).
`kind` **денормализуется** в `anchor_plan_items` и `placements` при создании — чтобы
фильтры/статистика были быстрыми и чтобы тип был явно виден в каждой сущности (требование ТЗ).

**Где показываем бейдж «Наши/Клиентские»:** список задач, карточка размещения, кабинет
сотрудника, анкор-план, отчёты, аналитика, журнал действий (единый компонент §6).

**Как исключаем смешивание:**
- При импорте плана `kind` фиксируется на плане → наследуется всеми строками.
- Матчер (`auto_match_plan`) работает **в рамках одного плана**, значит анкор из клиентского
  плана физически не может попасть на строку «нашего» плана (и наоборот) — доноры общие,
  но анкоры/строки принадлежат конкретному плану.
- Назначение сотрудникам и «Мои задачи» получают фильтр `kind`.
- Валидация на `mark_placed`: `placement.kind` берётся из строки/плана, руками не меняется.

## 9. Распределение работы сотрудников (соотношение «наши/клиентские»)

**Настройка соотношения (`allocation_settings`):** приоритет
`employee > team > global`; опционально период. Пример: global 50/50, у сотрудника Иванов — 70/30.

**План/факт (`employee_daily_plans`, можно и вычислять):** дневной и месячный план,
разбивка internal/client, факт, **отклонение** от соотношения.

**Алгоритм авто-раздачи** (расширение `assign`): для сотрудника с планом N и соотношением
p/q система стремится выдать `round(N*p)` внутренних и `round(N*q)` клиентских **строк,
уже прошедших подбор** (`selected_donor_id` задан) и не нарушающих существующие ограничения:
гео, язык, доступность донора, стоп-лист, повторное использование донора, требования проекта,
приоритет проекта, (в будущем) навыки/доступы сотрудника. Если по одному направлению нет
задач — добираем из другого, но **фиксируем отклонение** и показываем его в статистике.
Ручная корректировка менеджером/тимлидом — через UI (пере-назначение строк).

**Важно:** соотношение влияет только на **раздачу задач сотрудникам**, а не на подбор доноров —
подбор остаётся общим и уже корректно изолирован по анкорам.

## 10. Проверка ready-link

`result_url` в `placements` уже хранит опубликованную страницу. На `mark_placed` создаём/обновляем
запись в `link_checks` (статус `pending`) и ставим в очередь. Сохраняем ожидаемые:
`expected_url`(target), `expected_anchor`, `expected_link_type`, дату, сотрудника, проект, `kind`.

**Многоуровневая проверка (не браузер по умолчанию):**
1. **L1 — HTTP + HTML:** `httpx` GET (с редиректами, лимит размера/времени), парсинг ссылок
   (`selectolax`/BeautifulSoup): ищем `<a href>` на target-домен, сверяем анкор и `rel`
   (dofollow/nofollow), учитываем ссылки в тексте/кнопках/картинках.
2. **L2 — редиректы/финальный URL:** разбор цепочки редиректов, сверка конечного URL.
3. **L3 — headless (Playwright), только если** контент рендерится через JS или L1/L2 не дали
   однозначного результата. Тяжёлый образ → за флагом/в отдельном воркере.
4. **L4 — ручная проверка:** если авто невозможно (CAPTCHA/блокировка/логин).

**Нормализация при сравнении URL** (общий модуль `services/url_match.py`): схема http/https,
www/без www, завершающий `/`, UTM и прочие GET-параметры, URL-кодирование, редиректы,
абсолютные URL. Совпадение анкора: точное / бренд / URL-анкор / **безанкорное** (ссылка есть,
анкор пустой/технический). Всё это — чистые функции с юнит-тестами.

**SSRF-защита (обязательно, §13):** валидация схемы (только http/https), резолв хоста и
**запрет приватных/loopback/link-local IP** (в т.ч. защита от DNS-rebind — проверка IP после
резолва), лимит редиректов, таймаут, лимит размера ответа, без доступа к внутренним хостам.

## 11. Периодические проверки + фоновый обработчик

- **Первая проверка** — сразу после `mark_placed` (enqueue, `next_check_at = now`).
- **Повторная** — раз в сутки (`next_check_at = last + interval`); интервал настраивается админом.
- **Очередь — в БД** (`link_checks`), воркер забирает пачку `WHERE status IN(pending, due)
  AND next_check_at<=now` с блокировкой (`locked_at` + `SKIP LOCKED`/оптимистичный клейм).
- **Воркер:** asyncio-задача в `lifespan` (как heartbeat) с семафором на N одновременных
  проверок; ретраи с backoff при временной ошибке; таймаут; **задержка между запросами к
  одному домену** (вежливость); защита от бесконечных повторов (`attempts` cap → `manual`);
  логирование; приоритет очереди; ручной перезапуск (`/placements/{id}/recheck`).
- **Планировщик** периодики — тот же цикл по `next_check_at`, либо Railway Cron.
- **Масштабирование:** очередь в БД спроектирована так, что воркер позже выносится в
  **отдельный Railway-сервис** (тот же образ, `WORKER_MODE=1`, без веба) без переписывания.
  Полноценный Celery/Redis на старте не нужен (лишняя инфраструктура/деньги).

## 12. Статусы проверки (не сливать в один)

`pending` (ожидает), `checking` (проверяется), `found` (ссылка найдена),
`not_found` (не найдена), `wrong_url` (неправильный URL), `wrong_anchor` (неправильный анкор),
`anchor_changed` (анкор изменён), `page_unavailable` (страница недоступна),
`redirect` (редирект), `auth_required` (нужна авторизация), `blocked_captcha` (CAPTCHA/блок),
`temporary_error` (временная ошибка), `check_error` (ошибка проверки),
`manual_required` (нужна ручная проверка).

Для каждого результата в `link_check_results` храним: дату/время, HTTP-статус, найденный URL,
найденный анкор, ожидаемый URL/анкор, финальный URL после редиректов, тип ссылки, причину
ошибки, технический ответ (raw), длительность. **История, а не только последний результат.**

## 13. Риски и пограничные случаи

| Риск | Митигируем |
|---|---|
| **SSRF** через ready-link | белый список схем, запрет приватных IP (после резолва), лимит редиректов, таймаут, лимит размера, без внутренних хостов |
| Утечка данных между клиентами | скоуп по `client_id` в SQL, отдельные `ClientXxxOut`, тесты прямых API-запросов |
| Смешивание «наши/клиентские» | `kind` на плане → наследование, подбор в рамках плана, фильтры на назначении |
| Ложные срабатывания проверки | нормализация URL/анкора, многоуровневость, статус `manual_required` вместо «удалено» |
| Агрессивный трафик на доноров | per-domain задержка, семафор, backoff, дневные лимиты |
| Блокировка backend'а тяжёлыми проверками | воркер вне request-loop, семафор, позже — отдельный сервис |
| Playwright раздувает образ/память | за флагом, только L3, при необходимости отдельный воркер |
| Совместимость с текущими данными | `DEFAULT 'internal'`, nullable FK — старые данные = «Наши», потоки не ломаются |
| Расширение ролей ломает `require_admin` | `require_admin` остаётся admin|super_admin; новые роли добавляются, не переименовываются |
| Стоп-лист (см. ниже) | остаётся глобальным по `target_url` |

**Архитектура стоп-листа (ответ на вопрос ТЗ):** **единый глобальный** стоп-лист, ключ
`(target_url, anchor_text, donor_url)` — **комбинированный** подход: физический дедуп остаётся
глобальным (на одной странице донора одна и та же продвигаемая ссылка не может стоять дважды —
это физика, независимо от владельца), а `target_url` уже разделяет клиентов (у разных клиентов
разные продвигаемые URL). Добавляем **теги** `kind`/`client_project_id` только для отчётности и
фильтров. Раздельный по клиентам стоп-лист **вреден** — позволил бы поставить одну ссылку на
донора дважды. Правило «не назначать донор, если та же продвигаемая ссылка там уже была»
сохраняется без изменений.

## 14. Пошаговый план (маленькие обратимые этапы)

Порядок: **БД → серверная логика → API → интерфейс → фоновый сервис → тесты.** Каждый этап
самодостаточен, обратно совместим, деплоится отдельно.

| Фаза | Содержание | Критерий приёмки |
|---|---|---|
| **0** | Аудит (этот документ) | — |
| **1. Типизация «Наши/Клиентские»** | миграция `kind` (default internal) на plans/items/placements/stoplist; наследование при создании; фильтр `kind` в списках; бейдж в UI | все текущие данные = «Наши»; фильтр работает; ничего не сломалось; бейдж виден везде из §8 |
| **2. Клиенты и проекты** | таблицы `clients`, `client_projects`, `client_project_members`; CRUD API; UI списки/карточки; связь клиентского плана с проектом | создать клиента+проект; импортировать клиентский план, привязанный к проекту; он помечен `client` |
| **3. Роли + клиентский кабинет** | enum ролей (+manager/teamlead/client), `users.client_id`, RBAC-зависимости, `/client/*` со скоупом, страницы кабинета, тесты изоляции | клиент видит только свои данные; прямой API к чужому/внутреннему → 403/404; внутренние данные не видны |
| **4. Распределение работы** | `allocation_settings`, `employee_daily_plans`, авто-раздача по соотношению с фиксацией отклонения, UI менеджера/тимлида | 50/50 при плане 50 → ~25/25; при нехватке одного направления — добор + отклонение в статистике; ручная корректировка работает |
| **5. Проверка ready-link (ядро)** | `link_checks`+`link_check_results`, статусы §12, L1/L2 HTTP-проверка, нормализация URL/анкора, SSRF-защита, enqueue на `mark_placed`, ручной `recheck` | размещение ставится в очередь и проверяется; корректные статусы found/not_found/anchor_changed/redirect/unavailable; SSRF заблокирован (юнит-тесты) |
| **6. Фоновый воркер + периодика** | asyncio-воркер (семафор, per-domain задержка, ретраи/backoff, таймаут, приоритет), ежедневный ре-чек, настраиваемый интервал | пачка ссылок проверяется не блокируя API; ежедневный ре-чек идёт; лимиты соблюдаются |
| **7. Headless L3 (Playwright)** | опционально, только на неоднозначных результатах, за флагом | JS-страница, где L1 не нашёл, — определяется на L3 |
| **8. Контроль/аналитика** | страница `link_monitor` со сводкой (§10) и всеми фильтрами; статистика по проектам/клиентам/сотрудникам/донорам | сводка показывает % сохранности и статусы; фильтры работают |
| **9. Уведомления** | таблица `notifications`, правила (пропала/анкор изменился/…); конфиг видимости статусов клиенту | менеджер получает уведомление о пропаже ссылки/смене анкора; клиент видит только разрешённые статусы |
| **10. Отчёты клиента** | выгрузка отчёта по проекту (CSV/PDF) в кабинете | клиент выгружает отчёт со своими размещениями и статусами |

**Для каждого выполненного этапа буду фиксировать:** изменённые файлы, добавленные миграции,
реализованную логику, как проверить результат, добавленные тесты, что осталось.

**Принципы:** ничего не удаляем и не ломаем; всё обратно совместимо; расширяем существующие
сущности/механизмы, а не дублируем; без заглушек/моков без рабочей серверной логики.
